# OptiVision — Code audit, market study, and a simpler organisation

**Date:** 16–17 August 2026 · **Scope:** `optivision/` (React 19 + Tauri v2), `APPLICATION_OVERVIEW.md`, `requirements/`, competitor research (Algeria, Maghreb, France, international).

> **Status update (17 Aug 2026).** Sections 1–4 are the diagnosis as found. Sections 5–7 were the proposal, and **most of it is now built and verified in the running app**: single data layer with one transactional "record a sale", line-based orders, payment history, traced stock movements, monotonic document numbering, the new sale screen ending in a printed invoice **and** a fiche d'atelier, the client file at `/clients/:id`, the 6-menu navigation with tabs, the caisse du jour, and plain-French statuses everywhere. What remains is listed in §8.

---

## 1. Verdict in one paragraph

The app looks finished and is not. Every screen reads from a browser `localStorage` store filled with mock data; the complete SQLite layer that was written (schema, migrations, query modules, hooks) is **dead code that no screen imports**. The central promise — *sale → invoice → payment* — is broken: `createFacture` is never called anywhere, so the sale flow cannot produce an invoice, and the invoices you see are seed data. Separately, the feeling of "too complex" is real but it is not caused by too many features; it is caused by **too many screens for one job** (three stock screens, prescriptions split from the client file, orders split from invoices), by **status codes shown as codes** (`NEW`, `ORD`, `ASM`…), and by a sale flow that ends on a "brouillon" instead of on a printed invoice and a workshop ticket. The fix is not to add features. It is to collapse 9 menu entries into 6, make one real sale screen that ends in paper, and commit to a single data model before writing another page.

## 2. What the code actually is today (verified)

### 2.1 Three parallel data layers, one of them alive

| Layer | Files | Used by |
|---|---|---|
| Zustand + `localStorage`, seeded from mock data | `src/stores/appDataStore.ts`, `src/lib/mockData.ts` (643 lines of fake data) | **All 12 pages** |
| SQLite via `@tauri-apps/plugin-sql` | `src/lib/database/*` (~1 100 lines) | Only the hooks below |
| React hooks wrapping SQLite | `src/hooks/*` (6 hooks) | **Nothing** — zero imports outside `hooks/` |

Confirmed with `grep`: no page or component imports `@/lib/database` or any `use*` hook. `src/lib/web/listeVerresWeb.ts` (251 lines) is a second implementation of `src/lib/database/listeVerres.ts` (294 lines) for the browser path. So the same feature exists twice, and the persistence you intend to ship exists once, unused.

The Rust side is fine and further along than the front end: `src-tauri/src/lib.rs` holds two real migrations creating `clients, ordonnances, fournisseurs, produits, mouvements_stock, commandes, commande_lignes, commande_verres, factures, facture_lignes, paiements, parametres, casses, listes_verres, liste_verre_items` with indexes and default settings.

### 2.2 Schema drift between SQLite and the TypeScript model

These will collide the day you connect them:

- **Line items.** SQL has `commande_lignes` / `facture_lignes` / `commande_verres` (an order can carry many products, and OD/OG lenses separately). The UI model has `Commande.monture_id?` + `Commande.verre_id?` — **one frame, one lens, no quantity, no per-eye lens**. An optician regularly sells two different lenses (OD ≠ OG), plus an accessory, plus a service.
- **Payments.** SQL has a `paiements` table. The UI has `Facture.montant_paye` only, and `FacturesPage` payment modal does `montant_paye += amount`. There is no payment history, no date, no method per payment, no "who took the money".
- **Identifiers.** SQL columns are `code` (`commandes.code`, `factures.code`); TypeScript uses `numero`. SQL has `montant_total`/`montant_paye`; TypeScript has `total_ht`/`total_ttc`.
- **Numbering.** Numbers are generated by counting existing rows in the store (`appDataStore.ts:97-99, 172-174, 197-199`). Delete one invoice and the next one reuses a number. For an invoice register that is not acceptable, in any jurisdiction.

### 2.3 Broken paths in the current build

- `ClientsPage.tsx:184` links to `/clients/${id}`. **That route does not exist** in `App.tsx` — clicking the eye icon lands on a blank page. There is no client file screen at all, which is exactly the screen an optician uses most.
- **No invoice can be created.** `createFacture` exists in the store and is called by nothing. `AccueilClientPage` ends at `createCommande` + a "Brouillon créé" card.
- **Stock moves silently.** `AccueilClientPage.tsx:349-354` calls `updateProduitStock(id, -1)` directly, and the store clamps with `Math.max(0, ...)`. Nothing writes a `MouvementStock`, even though the type and the SQL table exist. Stock can therefore drift with no trace, and a cancelled order never puts stock back.
- **Auth is decorative.** `authStore.ts` holds `admin/admin123` and `vendeur/vendeur123` in plaintext, persisted in `localStorage`; role checks are client-side only. Fine for a demo, must not reach a shop.
- **Tauri shell is default.** `tauri.conf.json`: window 800×600, `productName: "optivision"`, no minimum size, `csp: null`. A grid-heavy app at 800×600 will be painful.

### 2.4 Screen inventory (what the shop actually sees)

9 sidebar entries, 12 routes, ~12 000 lines of TSX. The heaviest files are the ones the user touches most: `AccueilClientPage` 831, `SearchableProductSelect` 600, `ProduitForm` 549, `ListeVerresPage` 510, `RechercheStockPage` 485, `FacturesPage` 445.

Genuinely good work already in there, worth keeping: the `OpticalInput` control with +/− stepping and `+/-` keyboard signs, lens matching with **transposition** (`lensMatchesFilters`, `AccueilClientPage.tsx:60-97`) — most cheap software does not do transposition — the Algerian coating vocabulary (`HC/HMC/BB/PEG/PEB`), the tariff-code table in `opticalTariffCodes.ts`, the invoice template with **amount in words in French** (`FacturePrintTemplate.tsx`), the kanban view of orders, and the daily lens list.

## 3. What comparable products do

### 3.1 The direct local competitor (the flyer you sent — Ocula Precision, 30 000 DA, lifetime licence)

Its advertised list is a precise description of what an Algerian shop expects. Translated and mapped:

| # | Ocula advertises | OptiVision today |
|---|---|---|
| 1 | Comfortable design, no computer experience needed | Partial — but 9 menus and code-like statuses |
| 2 | Lens price lookup + is it in stock | **Yes** (`RechercheStockPage` + tariff codes) — best-in-class here |
| 3 | Stock alerts before running out **and before expiry** | Threshold only; **no expiry date** (contact lenses, solutions) |
| 4 | Barcode label printing (plain labels + lens/frame labels) | **Missing** |
| 5 | Clients with their prescriptions | Yes (but split across two screens) |
| 6 | Sales, payments and customer debt tracking | Partial — running total, no payment history |
| 7 | Order tracking (in progress / ready / delivered) | Yes (kanban) |
| 8 | **Fast sale: price → client → sale → receipt → fiche d'atelier in under 2 minutes** | **Missing** — flow ends on a draft, no receipt, no fiche d'atelier |
| 9 | Supplier files, payments and debts to them | **Missing** (`Fournisseur` type exists, no screen) |
| 10 | Bon de commande generated from sales or manually | Partial (`Liste verres` is 80 % of this) |
| 11 | Professional invoices | **Yes**, good template |
| 12 | Cash register (la caisse) tracked in detail | **Missing** |
| 13 | Financial analysis and performance | Partial (`Rapports` + CSV) |
| 14 | Inventaire (physical stock count) | **Missing** |
| 15 | All printouts carry the shop's logo/name | Partial |

**Five real gaps: fast sale + fiche d'atelier, caisse, suppliers, inventaire, barcode labels.** Note what is *not* on their list: appointments, EHR, insurance/tiers-payant, e-commerce, multi-store. That is the local ceiling, and it is a low one — you can clear it.

### 3.2 Maghreb software (the same shop, same budget)

OpticWizard (Morocco) sells "ventes, paiements, **crédit client**, reçus et historique" with an offline-first cash register. OPTIKOS (NSE, Morocco) leads with the **purchase module** and an inventory utility with entry documents. GestOptic (open source, Morocco) is literally: devis, factures, bons de livraison, **fiches d'atelier**, stock (verres, montures, lentilles, accessoires), inventaire, and profit/CA/caisse analysis. Netoptis advertises "en un clic : fiches de montage, devis, factures".

**The regional module set is remarkably stable: Vente/Caisse · Client+Ordonnance · Stock+Inventaire · Achats/Fournisseurs · Atelier · Documents (devis, facture, bon de livraison, fiche d'atelier) · Statistiques.** Seven concepts. Not nine menus, and never a separate "prescriptions" list.

In Algeria specifically: Silwane OptimaX (IntelliX) positions on "de la commande à la facture", detailed verres/lentilles stock with all optical parameters, **multi-comptes and multi-caisses**, 200+ access rights, and phone support with TeamViewer intervention. Optic Vision Manager (NESOFT, Algiers) is the other named local product. The competitive differentiator locally is *support and trust*, not features.

### 3.3 France and international (what to borrow, what to ignore)

Mature systems (Ocuco **Acuitas 3**, Cosium, Optimum Live, MyEasyOptic, RevolutionEHR, Eyefinity/EDGEPro) are built around a **single patient view**: one screen showing records, prescriptions, dispensing, orders, payments and history together — plus diary, recalls, integrated card payments, NHS/mutuelle vouchers, BI dashboards, lab-order integration (VisionWeb/HELIX), equipment links.

Two lessons only:

1. **Borrow the single client view.** Every serious product has it; OptiVision's version is a dead link.
2. **Ignore the rest.** Tiers-payant, teleconsultation, e-commerce sync, EHR and lab EDI are answers to French/US/UK reimbursement and chain problems. Building them here costs months and sells nothing in Algiers.

One structural idea worth stealing from the labs (Optivision Inc., Eyefinity lab ordering, Ari's "Job Card"): the **job ticket is a first-class object** with its own status and its own printout. In your app the order and the workshop ticket are the same thing and it is never printed.

## 4. Why it feels complex — six concrete causes

1. **Three screens for stock.** `Stock` (`/produits`), `Recherche stock` (`/recherche-stock`), `Liste verres` (`/liste-verres`). All three answer "what about lenses?" A shop owner has to learn which of the three to open.
2. **Prescriptions are a top-level list.** No optician looks up a prescription without a client. `OrdonnancesPage` even opens a modal titled "Sélectionner un client" to create one — the screen is asking for the thing the user already has in hand.
3. **Two homes.** `Accueil` (dashboard) and `Vente client` (`/accueil-client`, itself titled "Vente client"). The route name and the label disagree, and the dashboard's first tile just links to the other home.
4. **Orders and invoices are separate screens for one event.** In the shop, a sale *is* an order *is* an invoice *is* a workshop ticket. Three menus, one reality — and the app can't even connect them (§2.3).
5. **Codes on screen.** `NEW / ORD / RCV / ASM / RDY / DLV / CAN`, `MON / VER / LEN / ACC / SRV`, `DRAFT / SENT / PAID / PARTIAL / OVERDUE / CANCELLED`, `ESP / CB / CHQ / VIR / AUT`. Labels are mapped in some places and raw in others. This is the single loudest "made by a programmer" signal.
6. **The sale ends nowhere.** Three steps, each with a "Passer" (skip) button, ending on a green card that says a draft was created and offers two links to other screens. The user's actual goal — hand the client a paper and send a ticket to the atelier — never happens.

## 5. Proposed reorganisation

### 5.1 Navigation: 9 → 6

```
┌ AUJOURD'HUI        the day: sales, orders to call, lenses to order, unpaid, caisse
├ NOUVELLE VENTE     F2 — one screen, ends with invoice + fiche d'atelier printed
├ CLIENTS            search-first; the client file contains prescriptions & history
├ COMMANDES          the atelier board + the "verres à commander" tab
├ STOCK              products · lens finder · movements · inventaire
└ ARGENT             invoices, payments, customer debts, caisse du jour
  ─────────────
  Administration ▸   Rapports · Paramètres · Sauvegarde · Utilisateurs
```

Deleted as top-level: `Ordonnances` (moves into the client file), `Recherche stock` (becomes a tab of Stock **and** stays embedded in the sale screen), `Liste verres` (becomes a tab of Commandes), `Factures` (folded into Argent). Administration collapses three entries into one group, closed by default — a vendeur never sees it.

### 5.2 The sale screen (the only screen that really matters)

One page, top to bottom, no wizard, no skip buttons, always visible total on the right:

```
[ 🔍 client: phone / name / code / birth date ]     → results appear as you type
   nothing found → [+ Nouveau client] inline, 4 fields, no modal

CLIENT  Benali Karim · 0555 12 34 56 · 3 achats · reste 2 000 DA  [changer]

ORDONNANCE   ○ 12/03/2026 (la plus récente, pré-sélectionnée)  ○ 05/01/2025  [+ nouvelle]
             OD −2.00 (−0.75) 90°   OG −1.75 (−0.50) 85°   EP 62

LIGNES       + Monture     Ray-Ban RB5154 noir            1 × 12 000
             + Verre OD    HMC 1.56 unifocal   ✓ en stock  1 ×  3 500
             + Verre OG    HMC 1.56 unifocal   ⚠ à commander 1 × 3 500
             + Autre       Étui / réparation / service
                                                   Remise [    ]
                                                   TOTAL   19 000 DA

PAIEMENT     Espèces ▾   Acompte [ 10 000 ]   Reste 9 000 DA
LIVRAISON    prévue le [ 23/08 ]   Notes atelier [                    ]

            [ ENREGISTRER ET IMPRIMER ]   → facture + fiche d'atelier
```

What changes versus today:
- **Lines, not one frame + one lens.** OD and OG separately, plus accessories/services. This is also what the SQL schema already expects.
- **Payment happens here.** The acompte is the most common Algerian case and today it is impossible in the sale flow.
- **It ends in paper.** One button prints the invoice and the fiche d'atelier, decrements stock *with a recorded movement*, pushes out-of-stock lenses into today's bon de commande, and returns to a clean screen ready for the next client.
- **No "Passer" buttons.** Walk-in with no prescription? Just don't fill the block. A skip button on every step teaches the user that steps are optional and that the app is a form, not a counter.
- **Keyboard.** `F2` new sale, `F3` search client, `F4` add line, `F9` save and print, `Échap` cancel. Shop staff type; they do not hunt for buttons.

Target: **under 2 minutes for a repeat client**, matching the competitor's headline claim.

### 5.3 The client file (build this — it is missing entirely)

`/clients/:id`, one page, four blocks: identity + balance owed · prescriptions (with "nouvelle ordonnance") · orders with their status · invoices with payments. One button: "Nouvelle vente pour ce client". This kills the `Ordonnances` menu on its own.

### 5.4 Plain words instead of codes

| Code today | On screen tomorrow |
|---|---|
| `NEW` | À préparer |
| `ORD` | Verres commandés |
| `RCV` | Verres reçus |
| `ASM` | Au montage |
| `RDY` | **Prête — prévenir le client** |
| `DLV` | Livrée |
| `CAN` | Annulée |
| `PARTIAL` / `OVERDUE` | Reste 9 000 DA / Impayée |
| `MON/VER/LEN/ACC/SRV` | Montures / Verres / Lentilles / Accessoires / Services |

Keep the codes in the database, never in the interface. Colour-code the board: red = to order, orange = at the lab, green = ready to call.

### 5.5 The five missing features, in the order they pay off

1. **Fiche d'atelier** — printed with the sale. Cheapest to build, closes the loop, everyone in the region has it.
2. **Caisse du jour** — opening float, sales in cash, out-payments, closing count, one-click print. Every Maghreb competitor leads with this; a shop owner checks it every evening.
3. **Fournisseurs + bon de commande** — the `Fournisseur` type and the daily lens list already exist; add a supplier, group the list by supplier, print a bon de commande, mark it received (which is what turns `ORD` into `RCV` and adds stock, with a movement).
4. **Inventaire** — a counting screen: filter, type real counts, see the écarts, validate, and post adjustment movements with a reason.
5. **Étiquettes code-barres** — labels for frames, and a small lens label. Needs a barcode field, a print sheet, and later a USB scanner in the search boxes (a scanner is just a keyboard, so the search-first design already supports it).

Deliberately **not** on this list: appointments, SMS campaigns, tiers-payant/mutuelle, multi-store, cloud sync, e-commerce. They are in the international products because those markets require them.

## 6. The decision to take before writing any more code

**Commit to one data model and one persistence layer, now.** Concretely:

1. Keep the SQL schema as the source of truth (it is the better model), fix the naming drift (`code` vs `numero`, `montant_total` vs `total_ttc`) in a migration `v3`, and add what is missing: `commandes.numero` unique, an `ordonnance_id` on lines where relevant, `produits.date_peremption` (contact lenses), `produits.code_barre`, a `caisse` / `caisse_mouvements` pair, `fournisseur_commandes`, `journal_audit`.
2. Put a single `repository` interface in front of it, with two implementations: `sqlite` (Tauri) and `memory` (browser demo, seeded from `mockData`). Every page talks to the repository — never to Zustand for domain data, never to `lib/database` directly. That removes the third layer instead of maintaining it.
3. Delete `src/hooks/*` and `src/lib/web/listeVerresWeb.ts` once the repository exists; they are duplicated logic that will drift again.
4. Numbering, stock movements and payments go **inside a transaction** in the repository, never in a component: `enregistrerVente()` writes order + lines + invoice + payment + stock movements + lens-list entries atomically, and returns the printable documents.

Without step 4, the connected app will produce wrong stock and wrong invoice numbers on the first crash or double-click.

## 7. Suggested order of work

| Phase | Content | Why here |
|---|---|---|
| **0 — Truth** | Repository interface + SQLite implementation + `enregistrerVente()` transaction + real numbering + stock movements. Delete dead layers. | Everything else is decoration until data is real. |
| **1 — The counter** | New sale screen (lines, acompte, print invoice + fiche d'atelier). Client file at `/clients/:id`. Plain-French statuses. | This is the app, in the user's eyes. |
| **2 — Six menus** | Navigation collapse, Stock tabs (produits · recherche verres · mouvements), Commandes tabs (atelier · verres à commander), Argent (factures · paiements · caisse). | Turns 9 screens into 6 without losing a feature. |
| **3 — The money** | Caisse du jour, payment history, customer debts, refunds/annulations with stock return. | What the owner checks daily. |
| **4 — Supply** | Fournisseurs, bon de commande, réception → stock, inventaire with écarts. | What the owner checks weekly. |
| **5 — Shipping** | Real auth (hashed, in SQLite), audit journal, SQLite backup/restore + auto-backup reminder, A4/A5 print check, Tauri window/branding/installer. | Cannot hand it to a shop without these. |
| **6 — Later** | Barcode labels + scanner, expiry alerts, client recalls (renewal / order ready / unpaid). | Real value, but only once the base is solid. |

Phases 0 and 1 are what actually turn a prototype into a product. Phases 2–3 are what make an inexperienced user comfortable.

## 8. What was built on 17 August 2026, and what is left

### Built and verified in the running app

| Area | What changed |
|---|---|
| Data | One layer (`src/lib/data/` + `appDataStore`). `src/hooks/`, `src/lib/database/`, `src/lib/web/` deleted. Persistence is a swappable adapter: `LocalStorageData` today, SQLite next, with no page changes. |
| The sale | `enregistrerVente()` writes order + lines + invoice + invoice lines + acompte + stock movements + supplier lens list **in one operation**. Verified end-to-end: FAC-2026-0004 / CMD-2026-0006 created from the screen. |
| Numbering | Monotonic counters persisted in the snapshot. Deleting a document no longer frees its number. |
| Order model | Real lines: monture, verre OD, verre OG, lentilles, accessoire, service — with quantities and per-line "à commander". |
| Money | `paiements` table with date, amount and method. Caisse du jour totals by method. Client balance on the client file. |
| Stock | Every movement recorded (entrée, vente, sortie, annulation) with before/after quantities, visible in Stock ▸ Mouvements. Cancelling an order returns stock. |
| Documents | Invoice now prints the **real sold lines** (it printed tariff-table prices before). New fiche d'atelier: correction table, articles, delivery date, montage/contrôle/client-prévenu lines, no prices. |
| Navigation | 9 menu entries → 6 (Aujourd'hui · Nouvelle vente · Clients · Commandes · Stock · Argent), administration collapsed. Old URLs redirect. |
| Client file | `/clients/:id` built — it did not exist and its link was broken. |
| Vocabulary | `src/lib/labels.ts` is the single source; no more `NEW/ORD/ASM` or `ESP/CHQ` on screen. |
| Dead UI | "Nouvelle facture"/"Nouvelle commande" buttons that did nothing now lead to the sale; eye icons open the client file; fake disabled pagination removed; duplicate "Impayée"/"Impayées" filters merged. |
| Backup | Export/import now includes payments, movements, lens lists and counters — a restore no longer loses money history or reuses invoice numbers. |

### Client critiques from the previous version — status

| Critique | Status |
|---|---|
| Type `+`/`-` on the keyboard to set the sign | **Fixed** — `-`/`+` flip the sign, `↑`/`↓` step by 0.25, a trailing sign is understood |
| Modify and delete a prescription after creating it | **Fixed** — in the sale screen *and* on the client file |
| Lens type chosen → check stock automatically | **Fixed** — "3 verre(s) disponible(s) en stock pour cette correction", live |

| Lens not in stock → ordered from supplier | **Works** — line flagged automatically, order opens as "Verres commandés", line lands on the day's bon de commande |
| Add/delete lens types and lenses | **Works** — full product CRUD in Stock ▸ Produits |
| Change the total price | **Fixed** — "Prix final (modifiable)" overrides the calculated total |
| Frame optional | **Works** — no monture line required |
| Step 3: no sphere/cylinder, only lens type | **Works** — correction comes from the prescription, only the type is chosen |

### Left to do

1. **SQLite adapter** — implement `DataStorage` against `tauri-plugin-sql` and align migration v3 with the model (`numero`, lines, payments, counters). The interface is in place; no screen changes needed.
2. **Real authentication** — hashed passwords in the database instead of `admin/admin123` in `localStorage`, plus an audit journal for deletions, price changes and restores.
3. **Suppliers** — supplier files, printable bon de commande grouped by supplier, receiving that turns "Verres commandés" into "Reçus" and adds stock.
4. **Inventaire** — counting screen with écarts and adjustment movements.
5. **Barcode labels**, contact-lens **expiry alerts**, client **recalls** (renewal, order ready, unpaid).
6. **Desktop packaging** — window size/branding in `tauri.conf.json`, A4/A5 print check on the shop's printer, Windows installer.
